# Keiko — концепция

Автономный агент, создаваемый прежде всего для собственного использования автора — не оболочка и не кастомизация существующего инструмента, а самостоятельный агент с собственной архитектурой и UX. Ни один из существующих (OpenCode, Aider, Goose, Claude Code, Codex CLI, Antigravity CLI) полностью не устраивает — по функциональности, автономности или по интерфейсу.

Детальное поведение интерфейса и внутренней механики агента вынесено в отдельный документ — `keiko-ux-spec.md`. Здесь — то, что задаёт рамку проекта и меняется редко.

## Мотивация

Проект делается в первую очередь для себя, не ради популярности, аудитории или конкретной платформы хостинга:

> «Проект я вообще для себя в первую очередь делаю»

Исходная причина — на рынке не видно агента (не модели — именно *агента*, харнесса вокруг модели), который был бы одновременно «балансным» и бесплатным/открытым:

> «"балансного" и притом бесплатного агента (агента, а не модели) я не вижу»

Из этого прямо следует критерий успеха: не количество пользователей, не конкуренция с существующими проектами по фичам, а то, станет ли Keiko инструментом, который его автор действительно предпочитает всем остальным.

## Язык и платформа

**Rust** — не потому что «Rust быстрее», а по совпадению с уже имеющимся опытом и удобством лично для автора, плюс практические свойства (single binary, быстрый старт, сильная типизация, хорошая база для терминальных приложений).

**Unix-like — единая категория, не Linux-first.** Linux, macOS, FreeBSD и другие POSIX-oriented системы рассматриваются как один класс, а не как три принципиально разные платформы:

> «Что macOS, что Linux, что FreeBSD — это Unix-like»

Windows не определяет архитектуру и не является обязательным требованием первой версии, но и не исключается искусственно.

## Unix как родная среда

Базовые Unix-примитивы — естественная часть среды агента, не что-то, что нужно прятать за собственными абстракциями:

> «Мне хватает cp/rm/mv»
> «Не добавлять абстракцию только потому, что абстракция существует»

Этот принцип проведён последовательно, а не только для файловой системы — он же определяет минимальный набор инструментов агента (см. `keiko-ux-spec.md`, раздел Tool System): поиск и git не стали отдельными built-in инструментами именно потому, что для них уже есть `rg`/`find`/`git`, доступные через `shell`.

## Filesystem и процессы

Filesystem-операции используют нативные системные механизмы и обычные Unix-инструменты — не собственный «виртуальный файловый менеджер».

Выполнение процессов не завязано принудительно на shell-семантику: базовый механизм — `exec(program, args)` напрямую, не `bash -c "..."`. Shell нужен только там, где реально требуется shell-семантика (pipelines, redirects, условные конструкции).

**Shell пользователя используется по умолчанию**, не навязанный Bash. Если пользователь работает в Fish — Keiko должна нормально работать с Fish, без принуждения выбрать shell при первом запуске:

> «Я сам давно использую Fish»

При необходимости shell переопределяется явно в конфиге (`[shell] program = "..."`).

## Environment awareness

Информация об операционной системе и окружении — критическая часть контекста агента, не сводится к простому «OS = Linux». Минимум: семейство и конкретная ОС, дистрибутив (если применимо), версия, архитектура, shell, package manager, доступные инструменты, service manager (если релевантно), текущая рабочая директория, значимые переменные окружения, характеристики проекта.

Причина — печальный опыт, когда агент, не зная конкретного дистрибутива, пытался использовать не тот инструментарий:

> «Часто я обращался к агенту для установки/настройки чего-то, и он, от незнания КОНКРЕТНОГО дистрибутива Linux пытался поставить софт через apt. На арче»

Environment discovery выполняется автоматически при старте сессии, не требует ручного заполнения юзером.

## Project context

Не статичный кусок информации, который агент один раз прочитал и игнорирует, а то, с чем агент активно работает: обнаруживает характеристики проекта, архитектуру, toolchain, существующие conventions, обновляет знания по ходу работы, использует при последующих задачах.

## Память и состояние

Память, история, session state и cache не засоряют рабочую директорию проекта:

> «Я считаю плохим хранить файлы с памятью/историей чата в дире проекта»

Для Unix-like систем состояние хранится в стандартных пользовательских директориях (XDG-подобное разделение): `config` — пользовательская конфигурация, `data` — persistent memory/sessions, `state` — изменяемое состояние, `cache` — воспроизводимые временные данные. Project-local файлы появляются только тогда, когда юзер явно хочет, чтобы конкретные данные были частью самого проекта.

Память хранится человекочитаемыми файлами (markdown/toml), не в БД — это осознанное решение, а не временное упрощение: оно напрямую определяет, как память редактируется (см. «Память в UI» в UX-спеке — просмотр через Keiko, правка через `$EDITOR`, без отдельного мини-редактора).

## Конфигурация — TOML

Основной пользовательский формат конфигурации:

> «Скорее всего, с конфигом на .toml (ибо меня задрали эти .json, не нужно компромисса между юзером и программой)»

TOML — только для конфигурации. Runtime state, memory, sessions, cache не превращаются в единый TOML-файл — у каждого свой формат и место (см. выше).

## Автономность

Keiko — агент, а не ручной интерфейс управления LLM. Должен самостоятельно анализировать задачу, исследовать проект, использовать инструменты, изменять файлы, выполнять команды, проверять результат (см. «Verify перед done» в UX-спеке), исправлять ошибки, доводить до конца без построчного ручного руководства со стороны юзера.

## Инструменты, MCP, skills

Минимальный набор инструментов и конкретный tool-контракт — в UX-спеке (Tool System). Здесь — только принцип: не заводить отдельный built-in tool там, где существующий Unix-инструмент уже решает задачу.

MCP, skills и подобные системы не являются обязательной частью первой версии и не определяют архитектуру — автор либо не пользовался ими, либо не получал существенной пользы:

> «Насчёт MCP, скиллов и прочего — этим я ТУПО НЕ ПОЛЬЗОВАЛСЯ большую часть времени, а меньшую оно ничего полезного не вносило»

Сначала — хороший самостоятельный агент, расширяемость — потом, если реально понадобится.

## Provider independence

Агент и модель разделены. Ценность проекта — в agent runtime, context management, tools, environment awareness и UX, не в конкретной модели.

Только нативный structured tool-calling — модели, не поддерживающие его нормально, не получают prompt-based fallback, а получают явный отказ Keiko работать с ними при старте (подробности и обоснование — в UX-спеке, раздел Providers). Первый провайдер-адаптер для реализации — OpenAI-совместимый, как наиболее универсальный и покрывающий большинство локальных/бесплатных серверов.

## Открытый код

Лицензия — **MPL-2.0**, выбор по личному предпочтению автора, а не в расчёте на максимальное число форков:

> «выбор лицензии падает на MPL 2.0, ибо она банально моя любимая. MIT или GPL 3.0 мне не нравятся»

## Название и лого

**Keiko** (稽古 — практика, тренировка) — название получено случайно, через цепочку словарной выдачи «кимоно → kimono, gi, judogi, karategi, aikidogi, keikogi», из которой выбрано звучащее самостоятельно `Keiko`. Смысловая связь с практикой/повторением — приятное совпадение, не заявленный маркетинговый ход; название не подчёркивает, что продукт — coding tool/CLI/AI agent (никаких суффиксов вроде Code/CLI/AI/Dev).

Лого — существующий SVG (стилизованная ладья/крепостная башня, белым по `#DC143C`), изначально сделанный для другого, давно заброшенного проекта, принят как есть, без переделок под цветовую схему интерфейса — лого и цветовая семантика UI являются разными, не связанными друг с другом визуальными контекстами.

## Хостинг

GitHub, а не GitLab — по практической причине: на бесплатном GitLab-аккаунте недоступна привязка биллинга (страна/платёжная система отсутствуют в списке), что вынуждает использовать только self-hosted раннер; на GitHub то же самое решается проще. Дополнительный, не основной фактор — если проект когда-нибудь «обрастёт», на GitHub проще будет найтись тем, кому он окажется интересен. Это не противоречит исходному «не для популярности» — популярность по-прежнему не цель и не критерий архитектурных решений, здесь просто выбор конкретного инструмента под конкретное ограничение.

## Философия

Главный принцип, применяемый последовательно ко всем частям проекта — от файловых операций до permissions и набора инструментов:

Не добавлять абстракцию только потому, что её можно добавить. Если Unix уже предоставляет простой примитив — использовать его. Если shell не нужен — не использовать shell. Если информация об окружении доступна системе — агент определяет её сам, не спрашивает юзера. Если память не относится к проекту — не хранить её в проекте. Если расширение не приносит практической пользы — оно не обязательно только потому, что его используют другие агенты.

Keiko не обязан становиться популярным и не обязан конкурировать по числу пользователей с OpenCode, Aider, Claude Code, Codex CLI или кем угодно ещё. Единственный критерий успеха — стать агентом, которым его автор реально предпочитает пользоваться вместо существующих решений, не подгоняя реализацию под то, чем сам не стал бы пользоваться.
